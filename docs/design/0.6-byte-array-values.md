# 0.6 design: byte-array values in the type tree

Status: proposed for 0.6. Not implemented. Tracks the second half of
[#5](https://github.com/seiunx-dev/unity-rs/issues/5); the shader half shipped
earlier as caller-selected `ShaderReadLimits` in Python, Node and the CLI.

This is a breaking change to the public `TypeValue` and `TypeTreeReadLimits`
types, so it waits for a minor release.

## Problem

`TypeTreeValueReader` materializes every array element as its own `TypeValue`,
an enum of 32 bytes on 64-bit targets, and charges that size twice:

1. `read_array` charges `count * size_of::<TypeValue>()` for the `Vec` that
   holds the elements ("type tree array storage").
2. `read_node`, called once per element, charges `size_of::<TypeValue>()`
   again through `visit_node` ("type tree value storage").

A one-byte element therefore costs 64 bytes of `maximum_materialized_bytes`,
and also counts once toward `maximum_values` and `maximum_array_elements`. With
the defaults (512 MiB, 32,000,000 and 32,000,000):

| `vector<UInt8>` length | Result on 0.5.x |
| --- | --- |
| 8,380,000 | reads |
| 8,400,000 | refused: value storage passes 536,870,912 bytes |
| 16,800,000 | refused: array storage passes 536,870,912 bytes |
| 32,000,001 | refused: element count over 32,000,000 |

Real content hits this. In a Unity 6000.3.12f1 Android build, 65 of 669,905
MonoBehaviours are refused by `read_type_tree_json`; 64 of them are Live2D
`CubismMoc` objects whose `_bytes` field holds the raw moc (20,193,600,
27,990,336 and 44,999,616 bytes in the three examined). UnityPy reads all of
them.

## Goals

- A byte array costs about its byte length in the materialized budget, so a
  28 MB moc needs about 28 MB.
- Every container slot is charged exactly once.
- JSON and dump output stay byte-identical, so the managed differential and
  the Python and Node text outputs do not change.
- Limits keep bounding real heap use. None is removed.

Non-goals: zero-copy byte arrays, a new public JSON shape, and changes to how
`string` or `TypelessData` are read.

## Proposed change

### 1. A byte-array variant in `TypeValue`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ByteElement {
    /// `UInt8`, written as integers 0..=255.
    Unsigned8,
    /// `SInt8`, written as integers -128..=127.
    Signed8,
    /// A `char` whose node declares a byte size of 1, written as
    /// one-character strings, as `Character` is today.
    Character8,
}

pub enum TypeValue {
    // ... existing variants ...
    ByteArray { element: ByteElement, bytes: Vec<u8> },
}
```

`read_array` takes this path only when all of the following hold. Anything
else keeps the element-by-element path, so nothing about it is inferred:

- the array's data node is a leaf;
- its type is `UInt8`, `SInt8`, or `char` with a declared byte size of 1;
- the data node does not carry the align flag. An aligned element would need
  padding after every byte, and the fast path must not skip that.

The reader validates the count against the new byte limit (section 3),
reserves the `Vec<u8>` with `try_reserve_exact`, and reads the bytes with one
bounded read from the source `Region`. It does not create one `TypeValue` per
byte.

`bool` arrays stay on the element path, because each byte still has to be
checked as a valid boolean. A later change can add them with that check.

Owned bytes are chosen over the `TypelessData { offset, size }` form. The JSON
and dump writers work from `TypeValue` alone and have no access to the source,
and both still have to write every element.

### 2. Charge each slot once

`visit_node(depth, materialize)` already has a `materialize` flag. Each
container that charges for its slots up front (`read_array` per
`TypeValue`, `read_class` per `TypeField`, `read_map` per `TypeMapEntry`)
calls a `read_node` variant that counts the value toward depth and
`maximum_values` but does not charge `size_of::<TypeValue>()` a second time.
The root value, which no container holds, is charged once on its own.

The implementation audits each container, `SerializeReference` registries
included, against this rule. Tests assert the exact `materialized_bytes` of
small trees. Today's tests only check that the limit is enforced, which is
how the double charge went unnoticed.

A `ByteArray` charges `size_of::<TypeValue>()` for its slot, through its
container, plus `bytes.capacity()`.

### 3. Limits

- **`maximum_materialized_bytes` (512 MiB).** The default stays. The 512 MiB
  figure came from Live2D MonoBehaviours that charged 384 to 512 MiB under the
  double charge. After both changes the same objects charge much less, and
  their byte arrays no longer dominate. Fixing the double charge also lets
  element-wise arrays use about twice as many elements under the same budget:
  a 32-byte value now costs 32 bytes, not 64. The limit becomes an honest
  bound on retained heap, which its doc comment already claims it is.
  Lowering the default would refuse objects that read today, so 0.6 keeps
  512 MiB and re-measures it. Re-run the corpus with the new accounting and
  record the new measured maximum in the comment beside the default. Change
  the default only in a later release, and only with that evidence.
- **`maximum_array_elements` and `maximum_values` (32,000,000 each).** Both
  keep their defaults and keep applying to element-wise arrays. There, 32M
  elements already cost 1 GiB of slots, so the materialized budget refuses
  them first; the counts stay a coarse ceiling on absurd input. A `ByteArray`
  counts as one value and is not checked against `maximum_array_elements`.
- **New: `maximum_byte_array_bytes` (default 256 MiB).** Bounds one byte array,
  like `maximum_typeless_bytes` bounds one `TypelessData` blob. The default
  matches that 256 MiB figure and fits the largest moc seen (44,999,616 bytes)
  with room to spare. The cumulative bound remains `maximum_materialized_bytes`.

Downstream output budgets are separate and unchanged. For example, the 44,999,616-byte
moc as pretty JSON, one element per line, is larger than the default 256 MiB
`maximum_type_tree_json_bytes` of an export. That is an output decision for the
caller, not a parse refusal, and the release notes will say so.

### 4. Output

- **JSON** (`json.rs`): a `ByteArray` is written as the same array the
  element path writes, with the same indentation. `Unsigned8` and `Signed8`
  become integers. `Character8` becomes one-character strings, via the
  existing `Character` formatting. The writer streams from the slice, so it
  allocates no per-element values.
- **Dump** (`type_tree_dump.rs`): the same lines as today, element by element.
- **Expected-value builder** (`json.rs`, used by the TypeTree JSON tests):
  expands a `ByteArray` into the same `Value::Array`.
- The managed differential must stay byte-identical. It is the acceptance
  gate for this whole section.

## Migration impact

### Rust

- `TypeValue` is not `#[non_exhaustive]`, so the new variant breaks exhaustive
  `match`es downstream. 0.6 should make it `#[non_exhaustive]` in the same
  release, so that later variants are not breaking.
- Code that walks a byte vector as `TypeValue::Array` of `Unsigned`/`Signed`
  now gets `ByteArray`. Add accessors so callers do not match on the layout:
  `TypeValue::as_bytes() -> Option<&[u8]>` and
  `TypeValue::array_len() -> Option<usize>`.
- `TypeTreeReadLimits` gains a public field, which breaks struct literals that
  do not end in `..TypeTreeReadLimits::default()`.
- Core's own consumers (`live2d_schema`, `live2d_motion`, `live2d_physics`,
  `live2d_package`) match `TypeValue::Array` for float and object arrays only.
  Check each one, and add a test that feeds a byte array where one could
  appear.

### Python and Node

Neither binding exposes `TypeValue` or `TypeTreeReadLimits` on `main`. Type
trees reach them only as JSON or dump bytes (`read_type_tree_json`,
`read_type_tree_dump`, `read_mono_behaviour_json`, Live2D packages), using
Core's default limits. So:

- output bytes do not change;
- objects that are refused today (the 65 above) start to read. That is a
  behavior change for callers who relied on the refusal, and the release notes
  will name it;
- refusal messages for oversized byte arrays change: they name
  `maximum_byte_array_bytes` instead of value or array storage;
- no `.pyi` or `index.d.ts` change is needed unless the binding also exposes
  type-tree limits. If it does, `maximum_byte_array_bytes` /
  `maximumByteArrayBytes` is added with the Core default, and both API audits
  are updated.

If a structured type-tree reader lands in the bindings (the `read_type_tree`
on `codex/unitypy-compat`), map `ByteArray` to Python `bytes` and to a Node
`Buffer`, not to a list of integers. A 45 MB list of Python `int`s is gigabytes
of objects, which is what makes the branch take 1-2 s on these objects today.
That is an API decision, and it should be recorded in the binding's audit doc.

## Tests

- **Large moc-style array:** a synthetic `MonoBehaviour` with a
  `vector<UInt8> _bytes` of 44,999,616 bytes, built like the reproduction in #5.
  It reads with default limits, and its JSON is byte-identical to the
  element-wise writer's. Run it in release mode, or behind a size flag, if
  debug CI is too slow.
- **Boundaries:** byte arrays of exactly `maximum_byte_array_bytes` and of one
  more byte. Also exactly the remaining `maximum_materialized_bytes`, and one
  more byte. Each refusal stays in the limit error family with a stable
  message.
- **Exact accounting:** fixed trees (a scalar root, an object of three
  fields, an `int` array, a byte array, a map, a `SerializeReference`
  registry). Each asserts the exact materialized byte count, which pins the
  single charge.
- **Fallback paths:** an aligned one-byte data node, a two-byte `char`, a
  `char` of undeclared size (-1), and `bool` arrays all stay element-wise. Their
  output matches 0.5.x.
- **Malformed input:** a count beyond the remaining input fails before
  allocating. A negative count fails. A truncated byte run reports end of
  input, not a partial array.
- **Output parity:** the managed differential and the UnityPy oracle, where
  available, over fixtures with `UInt8`, `SInt8` and one-byte `char` arrays.
  The opt-in corpus run reports how many of the 65 objects now read, and their
  peak RSS.
- **Bindings:** the Python and Node API tests read the large synthetic object
  through `read_type_tree_json` / `readTypeTreeJson` with default limits, and
  check that the JSON is unchanged for the existing fixtures.
