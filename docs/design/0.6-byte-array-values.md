# 0.6 design: byte-array values in the type tree

Status: released in 0.6.0. Closes the second half of
[#5](https://github.com/seiunx-dev/unity-rs/issues/5); the shader half shipped
earlier as caller-selected `ShaderReadLimits` in Python, Node and the CLI.

This is a breaking change to the public `TypeValue` and `TypeTreeReadLimits`
types, so it waited for a minor release. The [migration notes](#migration-notes)
at the end list every public change and how to adapt.

## Problem

Before 0.6, `TypeTreeValueReader` materialized every array element as its own
`TypeValue`, an enum of 32 bytes on 64-bit targets, and charged that size
twice:

1. `read_array` charged `count * size_of::<TypeValue>()` for the `Vec` that
   holds the elements ("type tree array storage").
2. `read_node`, called once per element, charged `size_of::<TypeValue>()`
   again through `visit_node` ("type tree value storage").

A one-byte element therefore cost 64 bytes of `maximum_materialized_bytes`,
and also counted once toward `maximum_values` and `maximum_array_elements`.
Records (`TypeField`), maps (`TypeMapEntry`) and the `SerializeReference`
registry double-charged their values the same way. With the defaults (512 MiB,
32,000,000 and 32,000,000):

| `vector<UInt8>` length | Result on 0.5.x | Result on 0.6 |
| --- | --- | --- |
| 8,380,000 | reads | reads |
| 8,400,000 | refused: value storage passes 536,870,912 bytes | reads |
| 16,800,000 | refused: array storage passes 536,870,912 bytes | reads |
| 32,000,001 | refused: element count over 32,000,000 | reads |
| 44,999,616 (largest moc in #5) | refused: element count over 32,000,000 | reads |

Real content hits this. In a Unity 6000.3.12f1 Android build, 65 of 669,905
MonoBehaviours were refused by `read_type_tree_json`; 64 of them are Live2D
`CubismMoc` objects whose `_bytes` field holds the raw moc (20,193,600,
27,990,336 and 44,999,616 bytes in the three examined). UnityPy reads all of
them.

## Goals

- A byte array costs about its byte length in the materialized budget, so a
  28 MB moc needs about 28 MB.
- Every container slot is charged exactly once.
- JSON and dump output stay byte-identical, so the managed differential and
  the Python and Node text outputs do not change.
- Limits keep bounding real heap use. None is removed.

Non-goals: zero-copy byte arrays, a new public JSON shape, and changes to how
`string` or `TypelessData` are read.

## What was built

### 1. A byte-array variant in `TypeValue`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum ByteElement {
    /// `UInt8`, read element-wise as `TypeValue::Unsigned` 0..=255.
    Unsigned8,
    /// `SInt8`, read element-wise as `TypeValue::Signed` -128..=127.
    Signed8,
    /// A `char` whose node declares a byte size of 1, read element-wise as
    /// `TypeValue::Character` 0..=255.
    Character8,
}

impl ByteElement {
    pub fn value(self, byte: u8) -> TypeValue;   // the element-wise value
    pub fn type_name(self) -> &'static str;      // "UInt8", "SInt8", "char"
}

#[non_exhaustive]
pub enum TypeValue {
    // ... existing variants ...
    ByteArray { element: ByteElement, bytes: Vec<u8> },
}

impl TypeValue {
    pub fn as_bytes(&self) -> Option<&[u8]>;     // ByteArray only
    pub fn array_len(&self) -> Option<usize>;    // Array or ByteArray
}
```

`TypeValue` stays 32 bytes on 64-bit targets (a unit test pins it), so the
per-slot charge did not grow.

`read_array` takes the byte path only when all of the following hold. Anything
else keeps the element-by-element path, so nothing about it is inferred:

- the array's data node is a leaf;
- its type is `UInt8`, `SInt8`, or `char` with a declared byte size of 1;
- the data node does not carry the align flag. An aligned element would need
  padding after every byte, and the fast path must not skip that.

`bool` arrays, two-byte `char` arrays and `char` arrays of undeclared size
(-1) stay on the element path. A `bool` byte still has to be read as a
boolean; a later change can add it as another `ByteElement` with that check.

On the byte path the reader:

1. reads the count and refuses a negative one
   (`type tree byte array length cannot be negative: -1`) or one above
   `maximum_byte_array_bytes`;
2. applies the depth limit to a non-empty array exactly as the element path
   did, since its elements sit one level deeper;
3. refuses, before charging or allocating anything, a count beyond the bytes
   left in the object, with an end-of-input I/O error
   (`type tree byte array needs N bytes but only M remain`), so a truncated
   run never becomes a partial array;
4. charges the length, reserves it with `try_reserve_exact`, and reads the
   bytes with one bounded read from the source region (charging any capacity
   slack as well).

The root-field projection's skip path (`read_type_tree_root_field_with_limits`)
uses the same test and limits, and skips the bytes without reading them, so a
projection and a full read accept the same objects.

Owned bytes were chosen over the `TypelessData { offset, size }` form. The JSON
and dump writers work from `TypeValue` alone and have no access to the source,
and both still have to write every element.

### 2. Each slot is charged once

`read_node` now has two forms. `read_node` charges `size_of::<TypeValue>()`
for a value that no container holds: the root, a projected root field, and the
temporary `ReferencedManagedType` read while skipping a registry entry.
`read_slot` counts the value toward depth and `maximum_values` but does not
charge, because its container already paid for the slot:

| Container | Charges up front | Reads values with |
| --- | --- | --- |
| record (`read_class`) | `child_count * size_of::<TypeField>()` plus field names | `read_slot` |
| array (`read_array`) | `count * size_of::<TypeValue>()` | `read_slot` |
| byte array | its byte capacity (the slot is its container's) | one bounded read |
| map (`read_map`) | `count * size_of::<TypeMapEntry>()` | `read_slot` |
| registry entry (`read_referenced_object`) | `child_count * size_of::<TypeField>()` plus field names | `read_slot`, and the referenced type's root with `read_slot` |

The registry entry was the one container that grew field by field and charged
each pushed `TypeField` (budget message `managed reference field`). It now
counts its children and reserves them up front like a record (budget message
`managed reference field storage`). A null entry leaves its `data` slot
unused, but that slot is allocated, so it is charged.

Unit tests assert the exact `materialized_bytes` of a scalar root, a record of
three fields, an `int` array, a byte array, a map, a string field and a
`SerializeReference` registry, which pins the single charge.

### 3. Limits

- **`maximum_materialized_bytes` (512 MiB).** The default stays. It is now an
  honest bound on retained heap: each slot is charged once, and a byte array
  by its length. Element-wise arrays fit about twice as many elements under the
  same budget, because a 32-byte value now costs 32 bytes, not 64. The 512 MiB
  figure was set on a Unity 6000.3 Android corpus that is not available to this
  change, so it was not re-measured there; the comment beside the default says
  so. On the 135-bundle Project Sekai corpus used for the output parity below,
  the largest object needs 2,647,023 bytes of budget (2,647,087 under 0.5
  accounting), and the median object 2,794 (3,850). Change the default only in
  a later release, and only with a measurement on content that needs it.
- **`maximum_array_elements` and `maximum_values` (32,000,000 each).** Both
  keep their defaults and keep applying to element-wise arrays, where 32M
  elements already cost 1 GiB of slots, so the materialized budget refuses
  them first. A `ByteArray` counts as one value and is not checked against
  `maximum_array_elements`.
- **New: `maximum_byte_array_bytes` (default 256 MiB).** Bounds one byte array,
  like `maximum_typeless_bytes` bounds one `TypelessData` blob, and fits the
  largest moc seen (44,999,616 bytes) with room to spare. A longer one is
  refused with `type tree byte array length N exceeds limit M
  (maximum_byte_array_bytes)`. The cumulative bound remains
  `maximum_materialized_bytes`.

Downstream output budgets are separate and unchanged. The 44,999,616-byte moc
is about 160 MB as compact JSON and about 386 MB as pretty JSON, one element per
line. The pretty form is larger than the 256 MiB defaults of
`MonoBehaviourReadLimits::maximum_json_bytes`, `ExportOptions::maximum_type_tree_json_bytes`
and Python's `read_type_tree_json` / `read_mono_behaviour_json`, and export
writes pretty JSON by default. That is an output decision for the caller, not a
parse refusal: compact output (`--compact-json` on the CLI) or a larger output
budget writes it.

### 4. Output

- **JSON** (`json.rs`): `write_byte_array` writes the same framing as
  `write_array`, with the same indentation. `Unsigned8` and `Signed8` become
  integers, `Character8` one-character strings through the same string escaper
  `Character` uses. It streams from the slice and allocates no per-element
  value (a character is encoded into a stack buffer).
- **Dump** (`type_tree_dump.rs`): `write_byte_array` writes the same lines as
  `write_array`, passing `ByteElement::value(byte)` (a scalar, not an
  allocation) through the existing primitive path, so node validation and
  formatting are shared with the element path.
- **Expected-value builder and generator** (`json.rs` tests): expand a
  `ByteArray` into the same `Value::Array`, and the randomized round-trip test
  now generates byte arrays of all three element types.

### 5. Core consumers

`live2d_motion`, `live2d_physics`, `live2d_schema` and `live2d_package` read
arrays of records, strings, floats and references, never bytes. They now go
through a crate-private `TypeValue::element_values()`: an element-wise array
yields its values, an **empty** byte array yields an empty slice (the empty
list 0.5 read for it), and a non-empty byte array is refused as "not an
array", where 0.5 refused its first element instead. Each module has a test
for both cases. `live2d` (`_moc` `PPtr`), `export`, `mono_schema` and
`monobehaviour` match only records, strings and integers. `cubism_moc` reads
the moc with its own typed reader and does not go through `TypeValue`.

The CLI, Python and Node crates do not name `TypeValue` or
`TypeTreeReadLimits`; they reach type trees only as JSON or dump bytes with
Core's default limits, so none of their code changed.

### Deviations from the proposal

- `ByteElement` is `#[non_exhaustive]` too, and has `value` and `type_name`.
  `bool` is the obvious next element type, and adding it must not be another
  breaking change. `value` is what the writers use and what a downstream
  caller needs to rebuild the 0.5 shape.
- The depth limit still applies to a non-empty byte array. Dropping it would
  have quietly relaxed a limit the proposal does not mention.
- The registry entry charges its fields up front, rather than per push, so its
  capacity is what is charged.
- A truncated byte run is an `Io` `UnexpectedEof` error, the same family a
  truncated element-wise array produced, rather than `InvalidData`.
- The Live2D readers treat an empty byte array as an empty list, so their
  output for 0.5-readable input is unchanged.

## Evidence

- **Byte-identical output, real corpus.** A harness built against `main`
  (0.5.5) and against this change wrote, for each of the 2,822 objects in the
  135-bundle Project Sekai JP corpus (iOS, Unity 2022.3 layout), pretty and
  compact `read_type_tree_json`, `read_type_tree_dump`, and for the 534
  MonoBehaviours `read_mono_behaviour_json`: 9,000 outputs, the FNV-1a digest
  files are identical byte for byte. The corpus is not vacuous for the new
  path: 1,590 of its objects hold 1,747 `UInt8` byte arrays (76,652 bytes, the
  largest 7,746). It holds no `SInt8` or one-byte `char` vectors; those are
  covered below.
- **Byte-identical output, synthetic.** Unit tests compare the JSON writer's
  two paths on every byte value for all three element types, compact and
  pretty, empty and not, at the root and nested in records, arrays and map
  keys; and the dump writer's two paths for all three element types. The
  harness also wrote JSON (compact, pretty) and dump for 100,000-element
  `UInt8`, `SInt8` and `char` vectors and for the 8,380,000-element vector
  that 0.5 still read; all digests match 0.5.5.
- **Managed differential.** The managed oracle's dump fixture gained a
  `vector<UInt8>` and a `vector<SInt8>`; the managed dump and this project's
  agree.
- **UnityPy differential.** A new fixture with `UInt8`, `SInt8` (every byte
  value) and `bool` vectors agrees with UnityPy 1.25.0. One-byte `char`
  vectors are not compared there: UnityPy reads every `char` as an integer,
  where this project and the managed reader write a one-character string.
- **Budget.** `reads_moc_sized_byte_arrays_with_default_limits` reads a
  `CubismMoc`-shaped MonoBehaviour with `_bytes` of 8,380,000, 8,400,000,
  16,800,000, 20,193,600, 27,990,336, 32,000,001 and 44,999,616 bytes with
  default limits, and asserts each charges exactly its length plus the empty
  object's fixed cost. Boundary tests cover exactly `maximum_byte_array_bytes`
  and one more byte, and exactly the remaining `maximum_materialized_bytes` and
  one more byte, on both the read and projection paths.
- **Peak heap.** Measured with a counting allocator around
  `read_type_tree_value` on the same synthetic files, release build:

  | `_bytes` length | 0.5.5 | 0.6 |
  | --- | --- | --- |
  | 100,000 | 3,200,750 B (32x) | 100,750 B (1.0x) |
  | 8,380,000 | 268,160,750 B (32x) | 8,380,750 B (1.0x) |
  | 8,400,000 | refused after 268,800,866 B | 8,400,750 B (1.0x) |
  | 44,999,616 | refused | 45,000,366 B (1.0x) |

  0.5 used 32 bytes of heap per byte and charged 64; 0.6 uses and charges one.
- **Bindings.** The Python and Node API tests read a 44,999,616-byte `_bytes`
  through `read_type_tree_json` / `readTypeTreeJsonAsync` with default limits
  and compare the whole compact document, and pin a small document with
  `UInt8`, `SInt8` (and, in Node, one-byte `char`) vectors exactly.
- **Not run.** The opt-in `real_corpus` gate and the Unity 6000.3 Android
  corpus behind the 65 refusals in #5 are not available to this change, so how
  many of those 65 now read, and their peak RSS, is not measured here.

## Migration notes

### Rust (`unity-rs-core`)

| Change | Breaks | Adapt |
| --- | --- | --- |
| `TypeValue` is `#[non_exhaustive]` | exhaustive `match` outside the crate | add a `_ =>` arm |
| New `TypeValue::ByteArray { element, bytes }` | code that expects `TypeValue::Array` of `Unsigned`/`Signed`/`Character` for a byte vector | match `ByteArray`, or call `as_bytes()` |
| New `ByteElement` (`#[non_exhaustive]`), `ByteElement::value`, `ByteElement::type_name` | nothing | `element.value(b)` gives the 0.5 element |
| New `TypeValue::as_bytes()`, `TypeValue::array_len()` | nothing | use instead of matching the layout |
| New field `TypeTreeReadLimits::maximum_byte_array_bytes` (256 MiB) | struct literals without `..TypeTreeReadLimits::default()` | add the field or the default spread |
| Budget accounting: one charge per slot, byte arrays by length | budgets tuned to the old 64-byte charge now admit more | re-derive a hand-tuned `maximum_materialized_bytes` if it was meant as an element cap |
| A byte array counts as one value and is bounded by `maximum_byte_array_bytes`, not `maximum_array_elements` | code relying on those two limits to refuse long byte vectors | set `maximum_byte_array_bytes` |
| New error texts | code matching refusal messages | see below |

Which arrays become `ByteArray`: any array (usually a `vector`) whose data node
is an unaligned leaf `UInt8`, `SInt8`, or `char` with a declared byte size of
1, including empty ones. Examples: a MonoBehaviour `byte[]` field such as
`CubismMoc._bytes`, `Font.m_FontData`. Unity's `string` is still
`TypeValue::String`, and `TypelessData` is still `TypeValue::TypelessData`.

To keep code written against the 0.5 shape:

```rust
match value {
    TypeValue::Array(values) => use_elements(values),
    TypeValue::ByteArray { element, bytes } => {
        // The 0.5 element-wise values, if they are really needed:
        let values: Vec<TypeValue> = bytes.iter().map(|byte| element.value(*byte)).collect();
        use_elements(&values)
    }
    _ => not_an_array(),
}
// Or, for raw bytes:
if let Some(bytes) = value.as_bytes() { /* ... */ }
```

Error messages that changed or are new (all `InvalidData` unless noted):

- `type tree byte array length N exceeds limit M (maximum_byte_array_bytes)`
  replaces `array element count N exceeds limit 32000000` for byte vectors;
- `type tree byte array bytes raises materialized type tree bytes to N,
  exceeding limit M` replaces the `type tree value storage` / `type tree array
  storage` refusals for byte vectors;
- `type tree byte array length cannot be negative: N`;
- `Io` `UnexpectedEof`: `type tree byte array needs N bytes but only M remain`;
- `managed reference field storage raises materialized type tree bytes ...`
  replaces `managed reference field raises ...`;
- the Live2D readers report a non-empty byte array where they expect a list as
  `... is not an array`.

### CLI, Python and Node

- No signature, option, `.pyi` or `index.d.ts` change. Neither binding exposes
  `TypeValue` or `TypeTreeReadLimits`.
- JSON and dump output is byte-identical for every object 0.5 read.
- Objects 0.5 refused for byte-vector size now read: `read_type_tree_json` /
  `readTypeTreeJson`, `read_type_tree_dump`, `read_mono_behaviour_json`, export
  and the CLI. Callers that relied on the refusal, for example to fall back to
  raw bytes, now get the document instead.
- A large byte vector can now hit an output budget instead of the parse
  budget: a 45 MB moc is about 160 MB of compact JSON and about 386 MB pretty.
  Python's `read_type_tree_json` / `read_mono_behaviour_json` and the
  MonoBehaviour and TypeTree JSON budgets of export default to 256 MiB, and
  export (CLI included) writes pretty JSON unless asked for compact
  (`--compact-json`); Node's `readTypeTreeJson` defaults to 512 MiB. Such an
  object exports as compact JSON with the defaults, or as pretty JSON with a
  raised `maximum_bytes` / `maximumBytes` / export budget.
- Refusal messages for oversized byte vectors change as listed above.

If a structured type-tree reader is ever exposed (the `read_type_tree` on
`codex/unitypy-compat`), map `ByteArray` to Python `bytes` and to a Node
`Buffer`, not to a list of integers: a 45 MB list of Python `int`s is gigabytes
of objects. Both API audit documents record this.
